# iOS 多人大厅直接开始、地图进度与阵营选择优化设计

**日期：** 2026-08-27

**状态：** 已批准

**适用范围：** iPhone 与 iPad 横屏多人大厅；桌面 UI 与普通游戏 NotReady 确认流程不变，地图安全门禁由所有网络多人房间共享

## 目标

在不增加 iOS 大厅层级和确认步骤的前提下完成三项优化：

1. 房主点击“开始游戏”后，只要所有地图门禁满足就立即开始，不再弹出强制开始确认框。
2. 任何真人客户端尚未完成地图下载、安装/读取或服务器校验时都不能开始；界面必须显示具体阻塞者、阶段和可用进度。
3. 扩大 iOS 阵营/国家选择的可见内容和真实触控区域，减少滚动并提高旗帜可辨识度。

设计优先保持最小 iPhone 的现有主区域高度，不新增常驻状态栏或新的全屏步骤。

## 用户已批准的产品选择

- 仅改变 iOS 大厅 UI 与 iOS 房主开始流程；桌面继续保留原强制开始确认行为。
- 采用逐玩家地图进度同步，而不是只显示“已完成人数”。
- 下载具有可靠总长度时显示真实百分比；未知总长度、安装/读取和校验阶段显示不定进度，不伪造百分比。
- 未完成地图门禁时禁用开始按钮，并直接用按钮文字显示首要阻塞原因。
- 使用 iOS 专用的大尺寸阵营下拉，而不是新增全屏选择页。
- 所有已连接真人客户端都受地图门禁约束，包括因换图缩减 slots 而暂时无槽的客户端；机器人不参与。当前产品关闭观战入口，因此服务端必须明确拒绝新的无槽连接，并在换图造成真人失去 slot 时给出原因后移除，不能留下不可见的永久阻塞者。

## 平台边界与兼容策略

### iOS 可见行为

- iOS 房主使用新的安全开始路径。
- iOS 开始按钮显示动态阻塞摘要。
- iOS 玩家行的现有 Ready 状态单元格在地图未就绪时显示下载百分比、进行中或失败状态；就绪后恢复现有 Ready 控件/勾选。
- iOS 使用扩大的阵营按钮、弹层、旗帜和选项行。

### 桌面保持不变

- 桌面 `START_GAME_BUTTON` 继续按上游逻辑在存在未 Ready 玩家时打开 `FORCE_START_DIALOG`。
- 不删除 Force Start YAML、Fluent 文案或桌面按钮绑定。
- 不改变桌面玩家行、阵营按钮、弹层尺寸和旗帜布局。
- 所有网络多人房间共享“地图未完成绝不开始”的服务端硬门禁；桌面 Force Start 仍可忽略普通游戏 NotReady，但不能再踢掉仍在下载或校验地图的真人客户端。
- 协议 v22 的地图进度 publisher 必须在所有兼容客户端后台运行，包括桌面客户端；否则混合平台房间中的 iOS 房主无法判断远端地图状态。桌面不渲染新的 iOS 控件，也不改桌面交互。

### 协议版本

逐玩家进度和带当前地图 UID 的就绪握手属于联机协议合同，Orders 协议版本从 21 递增到 22。所有参与端必须使用兼容构建，避免旧服务端把新命令当成未知命令，也避免旧客户端只能提供含糊状态却被误判为完成。

## 组件边界

### `ClientMapReadiness`

为每个真人客户端维护当前选中地图的最小状态：

- `MapUid`：仅接受当前大厅地图 UID。
- `Phase`：`Unknown`、`Searching`、`WaitingForDownload`、`Downloading`、`InstallingOrVerifying`、`Ready`、`Unavailable`、`Error`。
- `Progress`：`-1` 表示不可量化；`0..100` 表示可显示的下载百分比。

该状态只描述“地图已下载并能被兼容客户端读取”，不声称客户端已经提前完成完整 World 加载。

### `ClientMapReadinessPublisher`

publisher 属于联机大厅会话/`OrderManager` 生命周期，不属于某个可隐藏的地图预览 Widget。这样直接连接、切换大厅 tab 和自动化 smoke 都会持续发布。所有协议 v22 客户端把本地 `MapPreview.Status`、`DownloadPercentage` 和当前地图 UID 映射为上述状态：

- 查询资源信息时为 `Searching/-1`。
- 可下载但尚未开始时为 `WaitingForDownload/-1`。
- 下载中且百分比已知时为 `Downloading/0..99`。
- 下载总长度未知时为 `Downloading/-1`。
- 文件已收完但仍在打开包、解析地图或等待成功回调时为 `InstallingOrVerifying/-1`；不能把 100% 下载视为 Ready。
- 本地地图成功进入 `MapStatus.Available` 后发布 `Ready/100`。
- 不可用或下载失败时发布对应失败阶段。

相位变化立即发送；同一整数百分比不重复发送；下载过程最多每客户端每秒四次。地图 UID 变化时立即重置，旧地图的异步完成回调不得污染新地图状态。

publisher 在 Local/Skirmish 大厅也可以发布同一份真实本地状态；这些模式继续接受既有 `state Ready/NotReady`，且不启用网络多人地图硬门禁。由 `RestartGame` 创建的 Local server 同样走这个明确兼容分支。

阶段和进度只允许以下组合，服务端拒绝其他组合：

- `Downloading`：`-1` 或 `0..99`。
- `Ready`：只能是 `100`。
- 其余所有阶段：只能是 `-1`。

### 服务端进度接收与同步

新的客户端命令只能更新发送者自身，不能指定目标玩家。服务端必须：

1. 严格解析枚举和进度范围。
2. 校验上报 UID 等于大厅当前地图 UID。
3. 拒绝陈旧 UID、非法阶段和越界进度。
4. 在换图时把所有客户端 `MapUid` 设为新的当前 UID、地图状态重置为 `Unknown/-1`，并把现有 `ClientState` 重置为 `Invalid`。
5. 在命令锁内立即把接受的阶段应用到服务端权威客户端状态；仅对随后发送给其他客户端的轻量增量做去重和限频。这样非 Ready 上报会立刻阻止开始，而每个百分点仍不会广播完整玩家列表或触发整套 Lobby UI 重建。
6. 让新加入者从完整 LobbyInfo 快照获得当前状态。

进度是客户端自报的 UX 数据。服务端放行不能只依据 `Progress == 100`，只能依据当前 UID 的 `Phase == Ready` 与既有客户端状态转换。任何 current-UID 非 Ready 阶段都会把客户端状态退回 `Invalid`；current-UID `Ready/100` 握手原子地更新地图状态，并只把 `Invalid` 转换成 `NotReady`。在 Multiplayer/Dedicated 中，普通 `state Ready/NotReady` 不能从 `Invalid` 解锁，且 `state Ready` 只在 current-UID 地图 Ready 时接受；Local/Skirmish 保留既有普通 state 转换语义并绕过网络地图门禁。

### `LobbyStartAvailability`

提取一个无 UI 依赖的开始判定模型，供 iOS UI 和服务器开局入口共同使用。模型只接收服务端拥有的数据：全局地图状态、客户端地图状态、slots、人数和出生点；地图安全子策略只读取 `Session.GlobalSettings.MapStatus` 与 current-UID 客户端状态。iOS UI 在此结果外用独立 overlay 叠加本机 `MapPreview` 可用性，不能把客户端本地文件事实作为同名参数传给服务器，也不能要求专服读取远端文件系统。结果包括：

- `CanStart`。
- 首要 `BlockReason`。
- 可选阻塞客户端索引、阶段和进度。

安全开始的全部门禁为：

- 发起者是房主/管理员。
- 服务器选中地图状态为 `Playable`，且不在 `Validating` 或 `Incompatible`。
- 所有已连接非机器人客户端针对当前 UID 都已进入 `Ready`，且不再是 `Invalid`。
- 必需槽已占用。
- 至少有一名入槽玩家。
- 禁止单人时至少有两名真人玩家。
- 可用出生点足够。

地图进度只负责解释阻塞，服务器接受的 current-UID Ready 状态才负责放行。现有无 UID 的 `state NotReady` 不得把当前地图从 `Invalid` 直接解锁；成功地图握手必须携带 UID，以消除换图与旧下载回调之间的竞态。

所有网络 Multiplayer/Dedicated 开局入口——新的安全命令、旧 `startgame` 和 `CheckAutoStart`——都必须先通过上述地图门禁，不能依赖可伪造的平台 capability。桌面房主仍保留普通游戏 NotReady 的 Force Start 兼容语义；本机 Local/Skirmish 和由 `RestartGame` 创建的 Local server 使用明确的可信本地启动分支，不要求不存在的网络地图握手。

### iOS 安全开始请求

iOS 不复用桌面强制开始路径，而发送新的安全开始命令：

1. 点击时重新计算 `LobbyStartAvailability`。
2. 若被阻塞，不发送命令；按钮保持禁用并显示原因。
3. 若可用，进入短暂 pending 状态并发送一次安全开始请求。
4. 服务端在同一权威模型上重新检查；通过才调用 `Server.StartGame()`。
5. 若同步竞态导致服务端拒绝，服务端返回结构化拒绝原因，客户端清除 pending 并刷新按钮；不能永久停在 `gameStarting`。

在 iOS 上，房主自己的普通游戏 Ready 勾选不再禁用开始按钮；是否可点击完全由安全开始门禁、当前 modal 和 pending 状态决定。命令验证器必须在房主已勾选 Ready 时仍允许安全开始命令，并允许必要的终态 `map_status` 重发。拒绝使用独立 payload，包含 reason enum 和可选客户端索引/阶段；iOS 在收到拒绝、断线或 5 秒超时后清除 pending。桌面继续发送原 `startgame` 命令并保留 Force Start 对话框。本任务不改变其兼容行为。

既有 `CheckAutoStart` 仍可在所有玩家主动勾选 Ready 后自动开始，但所有网络多人房间必须先复用同一地图门禁：服务器地图已 `Playable`，且所有已连接真人都对 current UID 地图 Ready。这样自动开始不能绕过下载或校验阻塞。

## iOS 交互设计

### 开始按钮与阻塞原因

不新增 footer 上方状态条，不压缩玩家列表或地图卡。禁用的开始按钮用短版本地化文字显示当前首要阻塞项；全部条件解除后恢复“开始游戏”。

优先级从高到低：

1. 服务器正在校验地图。
2. 地图不兼容或不可用。
3. 某客户端下载失败或地图不可用。
4. 某客户端正在安装/校验。
5. 某客户端下载中；有百分比时显示真实百分比。
6. 某客户端正在搜索或等待下载。
7. 必需槽未满。
8. 没有玩家、真人不足或出生点不足。
9. 其他既有配置门禁。

阻塞客户端按稳定的客户端索引顺序选择首项。存在多名阻塞者时，优先显示首项名称并附加简短剩余人数，例如“Kevin 下载 42% · 另 1 人”。如果动态玩家名使文案超过最窄按钮宽度，则整体切换为不含名称的短版，例如“2 人下载 · 最慢 42%”；不得只截断原因或百分比。中英文的完整短版必须在最窄 iPhone 的开始按钮内显示，不依赖 hover 或 tooltip。

### 玩家行状态单元格

复用现有 Ready 列的 48×48pt 物理触控单元，不增加列数或行高。common 玩家模板新增默认隐藏的 `IOS_MAP_STATUS_TEXT` 与 `IOS_MAP_STATUS_ICON`；它们只在 `Platform.IsIOS`、真人客户端 UID 等于当前地图且地图未就绪时显示，并与现有 checkbox/checkmark 严格互斥。机器人、陈旧 UID 和桌面永远隐藏这两个控件：

- `Downloading/0..99`：显示整数百分比。
- `Searching`、`WaitingForDownload`、未知长度下载：显示不定进行中标识。
- `InstallingOrVerifying`：显示校验/处理中标识。
- `Unavailable` 或 `Error`：显示错误标识。
- `Ready`：恢复现有 Ready 勾选/切换行为。

详细下载量与本机进度条继续使用既有地图卡。footer 提供全局首要原因，玩家行提供逐位状态，两者都不占用额外垂直空间。

### 阵营/国家选择

iOS 玩家行保持现有高度，重新分配列的最小物理宽度：

- 玩家名称至少 2 个 48pt 目标宽。
- 阵营按钮至少 3 个 48pt 目标宽，即约 144pt。
- 其余五列各至少 48pt。

对应布局策略的 `minimumPlayerWidth` 从 7 个触控目标提高到 10 个，并使用同一组显式列最小值；不能只改视觉权重而保留旧最小宽度。

阵营按钮的真实 `Bounds` 扩大，而不是只扩透明 `EventBounds`，保证按下、移动和释放使用同一命中范围。主按钮旗帜在 iOS 路径启用等比缩放和垂直居中，并为文字与下拉标记保留不重叠空间。

iOS 阵营弹层：

- 最小宽度为 5 个触控目标，约 240pt；扣除滚动条后仍保留约 190pt 内容宽。
- 高度以安全区和 6 个触控目标为上限；iOS 非交互分组标题压缩为 24pt、省略只有一个选项的冗余分组标题，并把 faction preset 的 `TopBottomSpacing` 设为 0；选项仍为 48pt。按 RA2 当前 `[3,1,5,4]` 分组，初始 viewport 必须完整显示至少 5 个可选择项。桌面继续显示全部原始分组标题和默认 spacing。
- 每个选项整行至少 48pt 高并可点击。
- 旗帜使用至少约 40×20pt 的等比视觉框，文字在旗帜右侧按实际字体和剩余宽度截断。
- 弹层、滚动条、旗帜、文字和选择项均保持 Safe Area containment，彼此不重叠。

不修改 common YAML 的桌面静态基线尺寸；所有放大和重新布局只在 `Platform.IsIOS` 路径应用。

## 状态流

```text
房主选择地图
  -> 服务端重置所有客户端为 Invalid + Unknown
  -> 客户端针对当前 UID 搜索/下载/安装并节流上报阶段
  -> iOS footer 与玩家行实时更新；开始保持禁用
  -> 客户端本地地图成功 Available
  -> 服务端接受 current UID Ready，转换为 NotReady
  -> 全部已连接真人地图 Ready + 服务器地图 Playable + 既有大厅门禁满足
  -> iOS 开始按钮恢复“开始游戏”
  -> 房主点击一次
  -> 服务端重新校验并直接开始
```

玩家的游戏 Ready 勾选与地图 Ready 是两层状态：地图 Ready 是能否安全进入对局的硬门禁；游戏 NotReady 在 iOS 房主安全开始时不再触发二次确认。也就是说，所有人地图完成后，即使有人尚未勾选游戏 Ready，房主仍可一次点击开始；地图未完成则绝不允许开始。

## 失败与竞态处理

- 下载失败：保留 `Error` 状态和玩家名，开始按钮显示失败原因；重试后进入新阶段。
- 下载或重试开始时先原子清零旧 `DownloadPercentage`/`DownloadBytes`，不能短暂复用上一次失败的百分比。
- 地图不可用：显示不可用原因，不允许开始。
- 未知 Content-Length：显示不定下载进度，不显示虚假 0%。
- 下载到 100% 但包仍在打开/解析：显示“正在校验/安装”，保持阻塞。
- 服务器 lint：显示全局“正在校验地图”及不定进度；只有 `Playable` 才放行。
- 服务器 lint 失败：显示地图不兼容，不允许开始。
- 换图：UID 不匹配的进度、完成回调和安全开始请求全部拒绝。
- 客户端断开：从阻塞集合移除；机器人始终忽略。
- 无槽真人：在被明确拒绝或因换图失去 slot 后移除前仍参与门禁；服务端必须发送原因并完成清理，不能留下隐藏阻塞者。
- 服务端拒绝开始：清除 iOS pending 状态并显示最新权威原因。
- 非法或过频进度：拒绝/合并且每客户端最多每 5 秒记录一次汇总诊断，避免日志放大，不影响服务器主循环。

## 测试合同

### 纯策略与协议测试

- 全局 `Validating`、`Incompatible`、非 Playable 均阻塞。
- `Invalid` 玩家和无槽真人都阻塞；机器人不阻塞。
- 所有地图 Ready、存在普通游戏 NotReady 玩家时，iOS 判定可直接开始，桌面仍判定需要 Force Start 确认。
- 必需槽、玩家数、双真人和出生点门禁保持不变。
- 进度状态序列化/反序列化覆盖 `-1`、`0`、`99`、`100` 和默认旧快照；服务端拒绝 `Ready/-1`、`Error/100`、`Downloading/100` 等非法组合。
- 命令拒绝陈旧 UID、非法枚举、越界进度和伪造目标玩家。
- publisher 覆盖相位即时发送、同值去重、每秒最多四次、换图重置和旧回调隔离。
- 安全开始命令在阻塞时不调用 `Server.StartGame()`，通过时只调用一次。
- `CheckAutoStart` 和旧 `startgame` 在下载、安装、校验或失败阶段不调用 `Server.StartGame()`；全部地图 Ready 后保持既有自动开始行为。
- 房主已勾选 Ready 时安全命令仍通过命令白名单；拒绝、断线和超时都会清除 pending。
- `Game.LoadMap`、Skirmish、同地图 Restart 不被网络握手门禁误伤；多人换图会重新进入门禁。
- iOS 房主即使已勾选普通游戏 Ready，仍能在其他地图门禁满足时点击一次开始；桌面禁用规则保持原值。

### iOS UI 与设备矩阵

覆盖 iPhone 844/932、iPad mini 1024/1133、iPad Air、iPad Pro：

- footer 和主区域几何不变，最小 iPhone 仍至少容纳一条完整 48pt 玩家行。
- 所有短版阻塞文案在中英文、两台 iPhone 上完整落入按钮，不省略、不越界。
- 玩家行百分比、进行中、校验、错误、Ready 状态正确切换。
- 新增的 iOS 状态 Label/Image 与 checkbox/checkmark 严格互斥，且桌面始终隐藏。
- 阵营按钮至少 144×48pt，其他列至少 48pt，所有列正尺寸、包含且不重叠。
- 最小玩家宽度和列最小值都使用 10 个触控目标合同，不能退回旧的 7 目标下限。
- 阵营弹层宽、高、可见行数、滚动条、旗帜和文字在 Safe Area 内且不重叠。
- 桌面 YAML 基线和桌面行为测试保持原值。
